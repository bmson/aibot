# Cloud Run workspace snapshot import

The manual **Import Firestore workspace snapshot** workflow reads one immutable private snapshot from the installation's workspace bucket and runs inside a Cloud Run job under the customer's service identity. GitHub Actions receives only the object URI, generation, SHA-256, source agent UUID, target database ID, and requested mode. It does not receive snapshot records or database credentials.

Start with `preview`. Copy the URI, generation, and SHA-256 exactly from the successful [source export](firestore-production-export.md) summary; choose the same source agent UUID and target database ID used during export. The job checks that the object belongs to this installation, pins the Cloud Storage generation on both metadata and byte reads, checks the byte size and SHA-256, validates the bundle's source and target identities, checks table coverage and record checksums, and computes the target document inventory. It does not write in preview mode. The workflow requires the released migration image to match the selected `main` commit.

`write` imports the validated bundle into an **empty** target installation. The importer creates a migration marker, writes deterministic batches, and can resume the same bundle after a partial failure. It refuses an occupied installation or a different bundle. `verify` reads every expected destination document, checks canonical checksums and collection counts, and reports parity. Keep the snapshot object, its generation, SHA-256, and job summary together for the cutover evidence record.

An unfenced source export is a **rehearsal** even when preview, write, and verify pass. A final cutover still needs a source write fence and drain, a new complete export and import, stored-object inventory, PostgreSQL-offline application rehearsal, full backup/restore, live runtime activation, and the [cutover checklist](firestore-cutover-checklist.md). Do not delete PostgreSQL based on this workflow alone.
